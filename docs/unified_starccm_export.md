# Единое окно экспорта STAR-CCM+ 2602

Окно конструктора теперь содержит восемь вкладок. Отдельного режима с другой формой
TMC нет; методика называется **TDC** и включается внутри общей подготовки расчёта.

## Что работает

1. **Сетка.** Оценка размера текущего ASCII Plot3D без разворачивания 3D-массивов;
   интерфейсы или Fuse между подканалами; сохранение секторов и поддерживаемая
   группировка стенок. При отдельных регионах объединение по физическому стержню
   недоступно. После Fuse исходные объёмные области создаются обязательно.
2. **Физика.** RST или HYBRID · SRH / SST; значения свойств из калькулятора y+
   доступны для проверки и изменения. IAPWS EOS допускает явно заданные постоянные
   вязкость и теплопроводность либо независимый выбор их методов IAPWS. Энергия при IAPWS обязательна. Настраиваются
   Reference Pressure, Initial Pressure, Initial Temperature и начальная скорость
   (нулевая, осевая из калькулятора либо VelocitySeed). Десятичная точка и запятая равноправны.
3. **Производные части.** Вертикальный список «Вся модель», «Подканал 1» и далее
   определяет области построения. Расположение плоскостей: не создавать, вход/выход,
   вход/середина/выход или равномерная серия из N плоскостей. Отдельно доступны
   осевые зонды подканалов и продольные плоскости зазоров. Зазоры показаны простым
   списком соседних пар без столбца площади. Пояснения перенесены в «?».
4. **Отчёты (Репорты).** Общие расходы и балансы; отдельный список подканалов и
   выбор геометрических, гидравлических, тепловых отчётов и трения. Используются
   мгновенные поля решения. Среднее по поверхности не означает среднее по времени.
   Выбор подканалов отчётов независим от областей построения плоскостей.
5. **Среднее по времени.** Постоянный `${timeStep}`; Second Order; SIMPLEC; Maximum Inner
   Iterations (по умолчанию 5); Maximum Steps выключается; Maximum Physical Time
   получает конец запланированного окна разгона и сбора средних для общего экспорта. Вызовы API выполняются с проверкой:
   отсутствие обязательного метода останавливает макрос с ошибкой, а не запускает
   расчёт с иными настройками. Повторный импорт сохраняет существующее решение.
   Вкладка активна только для нестационарного режима, включая RST. По умолчанию
   начало средних рассчитывается после разгона; ручной абсолютный шаг доступен
   для продолжения симуляции. Поля накапливаются общим окном; независимые блоковые
   скалярные статистики пока доступны только контроллеру эталона TDC.
6. **Качество.** Главный чекбокс выключен по умолчанию. Пороги доступны для изменения;
   выключенный этап не создаёт сцены, гистограммы, bad-cell наборы и отчёты качества.
   Неположительный объём входит в включённый этап. Обязательные проверки актуальности,
   полноты и конформности экспорта этим чекбоксом не отключаются.
7. **TDC.** Эталон S18/S22, два подканала, L=300 мм, P=11,64 мм, D=9,1 мм.
   Общие свойства и время берутся из тех же полей, что у обычного экспорта.
   Пользователь явно выбирает Fuse, SRH/SST, постоянные свойства, энергию,
   исходные rod-секторы и подтверждает три эквивалентных зазора.
   Несогласованные настройки блокируют сохранение, не меняются автоматически.
8. **Итог.** Сводка и управление вычислением физических отчётов. Автоматическая
   инициализация недоступна: для общего экспорта границы остаются wall, а для TDC
   периодичность назначается вторым макросом. Инициализируйте вручную после настройки.

Профили и проекты хранят вложенный словарь `workflow` версии 1. Старые профили без
него загружаются с миграцией признака качества и настроек прежнего TMC. Имена
внутренних ключей `tmc_settings`/`tmc_reference` сохранены для совместимости формата.
В новом комплекте файлы, Java-класс, параметры/отчёты и анализатор именуются TDC.

## Порядок TDC

1. Открыть/построить актуальную полную конформную эталонную сетку.
2. Настроить общую физику; включить TDC, проверить нагрев, расход и допущение трёх зазоров.
3. Сохранить комплект; выполнять сначала `setup_starccm_subchannels.java`,
   затем `TDC_Hybrid.java` с Action=0 на копии симуляции.
4. Проверить интерфейсы, свойства, знаки источника и сообщения ошибок; Initialize.
5. Action=1 — совместный гидродинамический и тепловой разгон без статистики.
   Action=2 также продолжает разгон с включённой энергией.
6. После установления явно разрешить статистику и Action=3 создать новую серию.
   Action=4 добавляет блоки; Action=5 выгружает; Action=6 показывает состояние.
   После каждого действия Action сбрасывается, решение не переинициализируется.

Контроллер связывает свой параметр шага с `${timeStep}`, обновляет Maximum Physical
Time перед очередным отрезком и отключает Maximum Steps. Блоковые скалярные средние
учитывают фактическое время; средние поля серии не сбрасываются на каждом блоке.
Boundary Heat Flux включён в опциональный набор средних полей контроллера.
`TDC_analyse_series.py` читает новые TDC-колонки CSV, а не прежние TMC-имена.

Температура для TDC — среднее по времени мгновенных среднемассовых температур,
с согласованным усреднением вдоль длины. `Mean of Temperature` не подменяет
мгновенную температуру в балансе. Коэффициент по принятой формуле статьи
безразмерный; это не отдельная размерная диффузивность в м²/с.

## Ограничения — показаны в окне

- Неконформный CFD-экспорт пока запрещён. Произвольное создание внутренних
  неконформных интерфейсов требует проверки импортёра и API STAR.
- Общее правило группировки сохраняет ТВЭЛ/НК/ИК раздельными. Независимый выбор правила для каждого типа и объединение всех rods пока не реализованы.
- Общий редактор поддерживает Wall, Symmetry, Mass Flow Inlet, Pressure Outlet, Internal, Internal + Periodic и Fully Developed + Periodic. Для входной турбулентности, обратного потока и явной настройки оси/угла периодического преобразования отдельных полей пока нет.
- Выбор стороны периодического интерфейса для каждого общего отчёта ещё не внедрён;
  обычный анализ использует измерительные сечения.
- Общие отчёты трения используют средний модуль напряжения. Они не являются
  осевой силой трения или полным КГС. Расширение на все физические типы стенок
  и осевую силу ещё требуется.
- Переменные транспортные методы IAPWS назначаются по записи команд 2602.
  Их фактическую работу нужно проверить в STAR-CCM+; локальные контракты не заменяют Siemens SDK.
- Для произвольной модели блоковый контроллер и отдельная настройка каждого
  монитора/графика пока не реализованы. Параметры блоков сохраняются, но применяются
  автоматически только для эталона TDC.
- Вызовы реальной STAR-CCM+ 2602 не проверялись в среде разработки. Java-контракты,
  исполняемый адаптер решателя и численное ядро тестируются без Siemens SDK.

Новые файлы сначала записываются временно. Отмена до публикации сохраняет старый
комплект; при ошибке замены выполняется откат. Если восстановление само не удаётся,
резервная копия сохраняется, а путь включается в сообщение ошибки.

## Проверки этой интеграции

Полный offscreen-прогон после компактного оформления: 226 тестов, OK (71,297 с). Дополнительно выполнен целевой прогон 13 новых проверок компактного окна, поверхностей и нагрева.
Новые регрессии проверяют восемь вкладок, качество по умолчанию, изменяемые пороги,
дробный ввод, свойства/начальные поля, профили, ограничения стенок, размер XYZ,
VelocitySeed, отчёты зазора, TDC-файлы и неактивные черновики.
Исполняется Java-адаптер Second Order/SIMPLEC/Stopping Criteria на явных контрактах;
сгенерированный TDC компилируется против тестовых API-контрактов. Это не проверка
Siemens SDK. Вкладки осмотрены на offscreen-снимках Qt.

## Компактное оформление и редактор поверхностей

Первую и вторую вкладки переработали в компактные формы. Длинные пояснения
перенесены в кнопки `?` с подсказками по наведению и пояснением по нажатию.
Флажок организации объектов называется «Папки объектов». Свойства и начальные
значения имеют ограниченную ширину; гравитация и направление расположены в строку.

Режим и турбулентность выбираются отдельно. RST доступен со стационарным и
нестационарным решателем; Hybrid SRH–SST требует нестационарного режима.
При IAPWS числовая сетка свойств скрывается, появляются селекторы транспортных
методов. Для каждого независимо доступны константа и IAPWS; классы методов взяты из пользовательской записи 2602.
Константы обновляются из текущего состояния калькулятора y+ автоматически при
изменении источника и по кнопке. Загрузка профиля не перезаписывается неизменившимся
источником калькулятора.

Функции `pi`, `Apert`, `thetaZ`, `seedX`, `seedY`, `VelocitySeed` и относительная
высота создаются автоматически. В начальной скорости можно выбрать VelocitySeed.
Функция назначается после её создания и до инициализации; повторный импорт не
перезаписывает начальные условия существующей задачи.

### Тепловой поток

В «Физике» флажок «Задать тепловой поток» открывает таблицу `q1 … qN` с точным
соответствием группам стенок. При изменении группировки таблица перестраивается:
сектора, физические стержни, стенки подканалов. Группы разных типов не смешиваются;
нагрев назначается только ТВЭЛ, НК и ИК исключены. Например, два подканала при
группировке по подканалу дают две строки, три — три строки.

В профиле сохраняются устойчивые идентификаторы групп и q, а не номера строк.
Неизвестная группа или изменившийся состав нагреваемых стенок блокирует экспорт.
Создаются скалярные функции поля `qN` с прямым числовым определением в SI и назначения Heat Flux на соответствующие
границы через записанный FunctionScalarProfileMethod. Повторный запуск того же
макроса сохраняет изменения q, сделанные в STAR. Новое значение из вновь
экспортированного макроса обновляет функцию поля; возврат к более раннему значению
тоже обрабатывается. Чужие функции поля с совпадающими именами не перезаписываются.

Выключенный флажок не назначает новые тепловые условия и не отменяет ранее
заданные пользователем условия в существующей симуляции. При включённом нагреве
требуется энергия. Для TDC нагрев теперь включается в «Физике»; все сектора одного
подканала должны иметь одинаковый q, Sub2 нагревается сильнее Sub1.

### Предпросмотр и интерфейсы

Предпросмотр построен по двумерным контурам фактических блоков. Он показывает
исходные области, стенки и внешние стороны; после Fuse внутренние линии остаются
пунктиром, но не выдаются за физические границы. Нажатие стенки выбирает её группу
в таблице q, нажатие внешней стороны — поверхность пары.

Для соседних раздельных подканалов таблица позволяет выбрать Internal либо Wall
(не соединять). После Fuse этот выбор неприменим: внутренние стыки объединены.
Для внешних поверхностей можно составлять пары Periodic с переносом. Проверяются
площадь, противоположность нормалей, совпадение формы после переноса и отсутствие
повторного использования. Вращательная периодичность не реализована. Произвольная
измерительная Plane Section не может быть выбрана как физическая граница.
Пары и отключённые внутренние сопряжения сохраняются в профиле и реально
передаются в макрос. Ориентацию и преобразование Periodic после импорта следует
проверить в STAR; фактический API 2602 в среде разработки недоступен.

У эталона TDC боковые пары задаёт его контроллер; общий редактор не добавляет
к ним дополнительные пары. Удалить ранее выбранные общие пары можно и при
включённом TDC.

Группировка и имена поверхностей используют новую схему идентификации. Поэтому
для общего экспорта после этой модернизации используйте новую пустую симуляцию
или её отдельную копию: макрос откажется менять несовместимую ранее импортированную
топологию. Изменение списка интерфейсов также требует новой совместимой сетевой
конфигурации; решение не переимпортируется молча.


### Запись дополнительных команд 2602

Источник — `addtion_command_macros.java`, добавленный пользователем в main
(fc995e6). Перенесены итоговые команды `IapwsDynamicViscosityMethod`,
`IapwsThermalConductivityMethod` и `FunctionVectorProfileMethod.setFieldFunction`.
Промежуточные переключения моделей, ошибочный `sin*`, недописанная ссылка `$t_end}`
и абсолютный путь импорта не переносятся.

Общий редактор осевых интерфейсов использует команды Fully Developed Periodic из записи.
`ReferenceDensity` и `MinimumAllowableWallDistance` доступны в опорных значениях.
Базовые Mass Flow Inlet / Pressure Outlet используют стандартные классы профилей;
для завершённой настройки входной турбулентности и обратного потока нужна запись
этих опций. Явная настройка вращательного преобразования требует записи оси/центра/угла
и примера пары. Автоматическое повторное назначение условий рассчитанной задачи
не включается без отдельного режима.

Проверка интеграции дополнительных команд: полный offscreen unittest — 228 тестов, OK (75,437 с). Реальный STAR-CCM+ не запускался.


### Опорные значения и дерево граничных поверхностей

`Minimum Allowable Wall Distance` задаётся в метрах, по умолчанию 1e-7 м.
Это ограничение физической модели, а не высота первой ячейки сетки. При гравитации
появляется `ReferenceDensity`: можно взять плотность из y+ либо задать отдельно.
Оба значения создаются как размерные параметры и назначаются опорным величинам.
Они применяются при первоначальной настройке; повторный импорт сохраняет физику.

В геометрии рядом со схемой расположено дерево реальных физических границ:
входы/выходы, стенки, боковые поверхности. После Fuse — один вход и один выход;
при отдельных регионах — свои для каждого подканала. Предпросмотр показывает
одну модель: над схемой выбирается вид «Боковые поверхности», «Вход» или «Выход».
Выбор границы в дереве автоматически переключает нужный вид. Выбор в дереве
и на схеме синхронизирован; Ctrl добавляет вторую поверхность. Пунктирная рамка
Qt отключена, выделение показывает цвет линии. Пунктир исходных стыков Fuse
сохраняется как геометрическая информация, это не рамка выделения.

Одна поверхность: Wall, Symmetry, Mass Flow Inlet (кг/с), Pressure Outlet
(избыточное давление, Па). Температура массового входа берётся из T_init;
турбулентность и обратный поток требуют проверки в STAR. Две поверхности:
Internal для совпадающих граней, Internal + Periodic, Fully Developed + Periodic
с положительным расходом (кг/с). Для Fully Developed первой выбирается вход,
второй — выход того же региона. Автоматический расход привязывается к существующему
G_subchannel; дублирующие параметры PeriodicMassFlow_N не создаются. Повторное
применение к той же паре обновляет её назначение.

Обычный Periodic оставляет стандартное преобразование STAR Rotational +
Translational: отдельного назначения оси/центра/угла в UI нет. До экспорта для
него проверяются площади; геометрическую трансформацию обязательно проверить в
STAR. В списке интерфейсов ровно три варианта: Internal, Internal + Periodic, Fully Developed + Periodic. Старые профили periodic_translation по-прежнему читаются с прежней дополнительной проверкой геометрии, но отдельного пункта в UI нет. Настройка Rotational со специальной осью будет добавлена после получения записи команд.
Совпадающие соседние границы можно назначить явно; тогда они исключаются из
автоматического поиска сопряжений. Выбор Wall в таблице соседей также сохраняется.

Проверяются повторное использование поверхности, конфликт одиночного условия и
интерфейса, устаревшие имена после Fuse/группировки и конфликт с нагревом ТВЭЛ.
При обнаружении ошибки профиль не применяется и экспорт блокируется.
Новые условия и интерфейсы включены в отпечаток конфигурации: смена назначения
требует новой тестовой симуляции, а не скрытой перестройки существующей.
Для эталона TDC условия по-прежнему задаёт его контроллер. Общие потоковые
отчёты используют соответствующие стороны периодического интерфейса;
непериодические случаи сохраняют прежние измерительные сечения.

Новые команды проверены генераторными регрессиями и Qt offscreen-тестами.
Реальный запуск новых типов границ, преобразования интерфейсов и опорных величин
в STAR-CCM+ 2602/компиляция с Siemens SDK в среде разработки не выполнялись.

Проверка редактора границ и опорных величин: полный offscreen unittest — 236 тестов, OK (86,866 с). Выполнены py_compile, git diff --check и осмотр Qt-снимков; Siemens SDK/STAR-CCM+ не запускались.


### Расчётный расход и упрощённая настройка частей

Для Fully Developed по умолчанию включён «Расход из y+». Используется та же
Re-зависимая опорная скорость, что в генерируемых параметрах Re_in / U_b:
`Dh = 4 A_total / P_wet_total`, `U_b = Re μ / (ρ Dh)`, `G = ρ U_b A_region`.
Площади и смоченный периметр берутся из текущей сетки; для отдельного региона —
его площадь, для Fuse — суммарная. Речь об опорном Re общей геометрии и свойствах
из калькулятора; при IAPWS это не локальное Re, меняющееся внутри расчёта.

Предварительное значение автоматического расхода показано в форме и сохраняется
в профиле для просмотра. В самом STAR интерфейс получает выражение, а не копию
этого числа. Для Fuse это `${G_subchannel}`. Поскольку G_subchannel в генераторе
рассчитан по суммарному сечению, для отдельного региона применяется
`${G_subchannel}*${S_in_SubN}/${S_in}`. S_in_SubN — площадь его живого сечения,
S_in — суммарная площадь. При общей опорной скорости сумма расходов подканалов
равна G_subchannel. Изменение глобальных Re_in / dynvis и других зависимостей
пересчитывает выражение в STAR без ручной замены расхода интерфейса.

Зависимости аналитического расхода создаются даже при отключении необязательных
параметров экспорта; последующее создание VelocitySeed не заменяет аналитический
U_b числовой копией. Флажок можно снять и задать ручной расход: число назначается
непосредственно величине интерфейса, также без отдельного PeriodicMassFlow_N.
Прежние ручные значения профилей сохраняются. Локальное изменение свойств IAPWS
в решении не означает изменение опорных глобальных параметров этого выражения.

Без уравнения энергии нагрев недоступен и не экспортируется. Сохранённые значения
q остаются для повторного включения энергии. При IAPWS энергия обязательна.

В новой настройке равномерной серии число N означает ровно N плоскостей,
включая вход и выход; скрытая дополнительная плоскость Z=L/2 не добавляется.
Для выбранных отчётов технические измерительные сечения входа/выхода могут
создаваться независимо от пользовательского набора плоскостей. Старые профили
с разными общими/подканальными сериями сохраняют прежние параметры до изменения
схемы пользователем. Средние поля по времени по-прежнему настраиваются в
«Среднем по времени»; отчёты новой вкладки автоматически на них не переключаются.

Проверка разделения частей/отчётов: полный offscreen unittest — 244 теста, OK (89,281 с). После последних правок отображения и выбора расхода — ещё 8 целевых тестов, OK (1,726 с). Выполнены py_compile, git diff --check и осмотр Qt-снимков; STAR-CCM+/Siemens SDK не запускались.


### Среднее по времени

Убрана верхняя техническая надпись о решателе. Основные поля: Δt [с], число
внутренних итераций, отрезок разгона [с], длительность блока [с], число блоков.
Для нового общего экспорта цель физического времени равна
T_runup + N_blocks·T_block, чтобы не остановиться до сбора средних.
Блоки здесь задают планируемое окно, без автоматического сброса полей на границах
блоков. Логика отдельного контроллера TDC не изменена.

Пролёт t_f=L/U_b показан по текущим опорным Re, свойствам и геометрии.
Рекомендации в «?» — предварительные ориентиры: 10–20 пролётов для разгона,
5–10 пролётов на блок. Они не заменяют проверку отсутствия дрейфа, времени
корреляции, согласованности последовательных блоков и достаточности окна.
У тепловой релаксации могут быть существенно более длинные времена.

При постоянном шаге N_start=ceil(T_runup/Δt)+1. По умолчанию номер вычисляется
автоматически и не занимает основную форму. Для продолжения расчёта можно
снять «После отрезка разгона» и задать абсолютный шаг. Прежние профили без
mean_start_auto сохраняют ручное начало. Повторный импорт уже существующих
FieldMeanMonitor сохраняет накопленные значения и прежнее событие начала.

«Функции для усреднения по времени» разделены на объём и стенки. Создаются
раздельные скалярные источники Velocity_i/j/k и WallShearStress_i/j/k,
а не один векторный выбор. Все поля имеют обозначения и размерности:
h₀ [Дж/кг], u/v/w [м/с], p [Па], T [K], ρ [кг/м³], μ [Па·с],
τw,x/y/z [Па], q″w [Вт/м²]. Плотность и вязкость доступны при IAPWS,
температурные/энергетические поля — при энергии. Старые векторные выборы
профиля преобразуются в три компоненты при загрузке окна. Прямой старый API
генератора продолжает принимать прежние ключи для совместимости.

Новые усреднённые скалярные мониторы расходов, ΔT, Re и других параметров не
добавлялись: их состав и методику сначала нужно согласовать. Выбор FieldMeanMonitor
не превращает отчёты вкладки «Отчёты» в усреднённые по времени отчёты.

Проверка вкладки средних: полный offscreen unittest — 249 тестов, OK (80,139 с). После последней правки ручного начала — ещё 5 целевых тестов, OK (1,792 с). Выполнены py_compile, git diff --check и осмотр Qt-снимка. STAR-CCM+/Siemens SDK не запускались.

Для постоянной теплоёмкости используется специализированный метод STAR `ConstantSpecificHeat` с привязкой `${Cp}`. Общий `ConstantMaterialPropertyMethod` применяется к плотности, вязкости и теплопроводности; Cp им не назначается. В IAPWS и без энергии эта настройка Cp не выполняется. Если первый импорт оборвался при настройке физики, исправленный макрос нужно запускать в новой пустой симуляции: повторный импорт не перезаписывает физику уже импортированной модели.


### Размерные функции теплового потока

В общем setup-макросе q1…qN создаются непосредственно в Field Functions,
с типом SCALAR и размерностью M¹L⁰T⁻³: Вт/м² = кг/с³. Определение — число
в SI из формы экспорта. Глобальные параметры qN и дополнительные HeatFlux_qN
не создаются; HeatFluxProfile получает сам объект qN. Для этой операции нет
обращения к UnitsManager.getObject("W/m^2"), поскольку имя такой единицы
не гарантировано в STAR. При группировке q-функции относятся к Thermal.

При идентичном повторном экспорте сохраняется выражение, изменённое в STAR;
новое заданное q заменяет его явным значением. Посторонние функции поля не
перезаписываются. Чужие/старые параметры автоматически не удаляются; после
неуспешного первого импорта используйте новую пустую симуляцию.
Этот путь относится к общему setup; отдельный эталонный контроллер TDC пока
сохраняет свою схему входов, которая дорабатывается на этапе TDC.

Привязка аналитического расхода входит в отпечаток конфигурации. Старый экспорт с числовым PeriodicMassFlow_N не объявляется совместимым и не сохраняет старую привязку незаметно: новый макрос проверяется в новой симуляции; существующие пользовательские условия автоматически не перезаписываются.

Начальная осевая скорость теперь напрямую ссылается на U_b: `[0, 0, ${U_b}]`. Параметр U_init не создаётся. Нулевая инициализация задаёт `[0, 0, 0]` только в профиле, не зануляя U_b/G_subchannel; VelocitySeed использует ту же опорную U_b. Требуемая аналитическая цепочка создаётся и при отключённых необязательных параметрах; числовой подмены U_b в Seed нет. Уже накопленное решение повторным импортом не переинициализируется, прежние пользовательские параметры автоматически не удаляются.


### Нестационарный решатель: записанный API STAR-CCM+ 2602

После пользовательского запуска с отказом SECOND_ORDER настройки переведены
на прямые вызовы из записи 21.02.007:
- ImplicitUnsteadySolver.getTimeDiscretizationOption(), тип TimeDiscretizationOption.Type.SECOND_ORDER;
- SegregatedFlowSolver.getSchemeOption(), тип ImplicitSchemeOption.Type.SIMPLEC;
- InnerIterationStoppingCriterion.getMaxIterations().getQuantity().setValue(double);
- StepStoppingCriterion.setIsUsed(false);
- PhysicalTimeStoppingCriterion.getMaximumTime().setValueAndUnits(now+duration, seconds).

Внутренние итерации и остановка по физическому времени явно включаются.
Вместо перебора setter-методов и имён опций используется типизированный API;
для VelocitySeed аналогично выбран прямой FieldFunctionTypeOption.Type.VECTOR.
Максимальное время определяется настройками окна, а не числом 50 из примера
рекордера. Java-контракт теста содержит раздельные типы опций и IntegerValue
с getQuantity(), поэтому прежние неверные getter-методы не проходят проверку.
После оборвавшегося первого импорта нужен новый пустой .sim: повторный импорт
сохраняет уже существующую физику и начальные условия.


### Периодические отчёты, зазоры и время

Для периодического входа/выхода отчёты используют дочерние `InterfaceBoundary`
соответствующей стороны, а не исходные поверхности Inlet/Outlet. Если сторона
не найдена или неоднозначна, макрос останавливается с объяснением. Для Fuse
отдельные подканалы выделяются маской на общей стороне интерфейса.

Каждый зазор получает локальную систему `Normal_Gap_SubA_to_SubB`:
ось Y направлена из A в B, X — вдоль зазора, Z — по высоте.
Нормальная скорость задаётся выражением
`$${Velocity}(@CoordinateSystem("Laboratory.Normal_Gap_SubA_to_SubB"))[1]`.
Средний MassFlux имеет знак и размерность кг/(м²·с); AbsMassFluxMean показывает
средний модуль локального переноса. Последний полезен при взаимно компенсирующихся
перетоках, но сам по себе не является TDC или мерой только турбулентного переноса.

Имена пользовательских функций синхронизированы; используются `Velocity_k` и
компоненты встроенной `Position`, без дублирующих AxialVelocity и X/Y/Z.
Геометрические отчёты и промежуточные расходы/свойства сохраняются, но лишние
мониторы для них больше не создаются. Для трения отслеживается Darcy; сохраняются
мониторы невязок, перепада давления и диагностик зазоров. Уже существующие
мониторы и их история автоматически не удаляются.

`Heat_Flux_Rods_Total` — мощность на стенках твэлов, Вт.
`Heat_Flux_Walls_Total` — мощность на всех физических стенках, включая твэлы, Вт.
Их нельзя складывать: первая выборка входит во вторую.

Новое планирование времени: `t_f=L/U_b`, разгон `N_runup*t_f`, длительность
блока `N_block*t_f`. Начальные ориентиры 10–20 и 5–10 пролётов требуют проверки
по отсутствию дрейфа и корреляции сигналов. Окончание не меньше суммы разгона
и `N_blocks*T_block`, округлённой вверх до Δt. Старые профили с секундами читаются.
В обычном экспорте N блоков пока задают **одно накопленное окно**, а не N
независимых результатов со сбросом средних. Контроллер эталонного TDC имеет
отдельную последовательность запуска и сбора; ручное окончание общего экспорта
не заменяет его управление этапами.

Проверки генератора включают offscreen Qt и исполнение Java-контрактов на
заглушках по записанному API STAR 2602. Они не заменяют запуск макроса в STAR.
