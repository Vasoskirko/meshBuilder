# Проверка экспорта Fuse в STAR-CCM+

## Группировка поверхностей

В режиме Fuse число внешних зазоров и стенок зависит от выбранной сборки. Правило «три наименьшие площади — зазоры» не применяется. Макрос сопоставляет площадь и центроид каждой боковой поверхности с геометрией фактически экспортированных блоков: половинами/полными гранями зазоров и дугами физических стержней. При неоднозначном или отсутствующем совпадении выполнение останавливается с сообщением о поверхности, а не присваивает ей тип стержня наугад.

Имена `rod_R<id>` соответствуют идентификаторам стержней геометрической модели, а не порядку сортировки площадей. В Fuse вариант «Секторы по 60°» недоступен: сохранение таких секторов после слияния не реализовано. Доступны группировка по физическим стержням и общая стенка. Угловое разбиение импортированной поверхности для её распознавания не является гарантией сохранения исходных секторов 60°.

Типы физических граничных условий пользователь задаёт вручную. Именование `Inlet`, `Outlet`, `rod_...`, `sym/per` само по себе не назначает вход, выход или симметрию.

## Сечения и зонды

После Fuse сохраняется один физический регион `TVS_Assembly`, но для анализа исходных подканалов создаются отдельные Threshold Parts `Subchannel_N_Domain`. Маска выбирает ячейки внутри исходного треугольника между центрами стержней. Номера соответствуют порядку подканалов в экспортированной сетке; пропущенные периферийные подканалы в него не включаются.

Индивидуальные сечения используют соответствующий Domain, а не весь монолит. Осевые зонды создаются по центру каждого выбранного исходного подканала. Общие сечения используют всю сборку. Ключевые положения Z=0, L/2, L не дублируются, если входят в регулярную серию. Для одного подканала совпадающее общее сечение переиспользуется. Отчёты расхода по подканалам требуют входного/выходного сечения даже при отключённой визуальной серии сечений.

## Отчёты и ошибки

- `MassFlow_Inlet_Total`, `MassFlow_Outlet_Total`: расходы по внешним входным и выходным поверхностям.
- `MassFlow_In_SubN`, `MassFlow_Out_SubN`: расходы через сечения исходного подканала. Нормаль всех таких сечений направлена по +Z; их знак не равнозначен знаку внешней нормали входной границы.
- `Imbalance_MassFlow`: `100 * abs(m_in + m_out) / max(abs(m_in), 1e-30)`. Для внешних границ используются знаковые расходы: вход обычно отрицательный.

При включённой энергии (или IAPWS, который включает энергию) также запрашиваются:

- `TotalEnthalpy_Inlet`, `TotalEnthalpy_Outlet`: средняя по массовому расходу полная энтальпия (`TotalEnthalpy`).
- `Energy_Flow_Inlet_Total`, `Energy_Flow_Outlet_Total`: массовый расход, умноженный на среднюю полную энтальпию.
- `Heat_Flux_Rods_Total`: интеграл `BoundaryHeatFlux` по стенкам стержней, мощность, а не плотность потока.
- `Heat_Flux_Walls_Total`: интеграл того же поля по всем внешним боковым стенкам, включая несопряжённые зазоры.
- `Imbalance_Energy`: относительный модуль `H_in + H_out - Q_walls`. Предполагается, что `BoundaryHeatFlux` положителен при подводе тепла к жидкости. Нормирователь — максимум модулей потоков энтальпии, тепловой мощности и `1e-30`.

Эта энергетическая невязка — диагностический стационарный баланс переноса полной энтальпии и тепла через боковые стенки. Она не учитывает накопление энергии в нестационарном расчёте, объёмные источники или дополнительные виды работы/переноса. Знак `BoundaryHeatFlux`, доступность полей и применимость такого баланса к выбранным физическим моделям необходимо проверить в целевой версии STAR-CCM+. Нулевые начальные значения при всех границах Wall не доказывают сходимость или выполнение энергетического баланса.

Для каждого успешно настроенного отчёта отдельно создаётся монитор. Ошибка монитора не прерывает создание следующих отчётов. Недоступное поле или ошибка STAR API выводится как `[!]` с именем объекта. Итоговый вывод показывает число созданных отчётов и мониторов, а не безусловное сообщение о готовности к расчёту.

## Приёмка в STAR-CCM+ 2602

Использовать новую пустую симуляцию и новый комплект XYZ/Java; старые макросы не обновляются автоматически.

1. Экспортировать два соседних внутренних подканала в Fuse, с одинаковыми параметрами блоков.
2. Проверить один регион, сохранность числа ячеек, положительные объёмы и отсутствие внутренней разделяющей стенки. Ноль отдельных интерфейсов в режиме Fuse ожидаем.
3. Проверить все четыре внешних зазора: они не должны называться стержнями. Проверить `rod_R<id>` по исходной геометрии, а не только по площади.
4. Включить каждую пару индивидуальных сечений на одном Z поочерёдно: каждое должно покрывать только свой подканал; сумма площадей должна соответствовать общему сечению. Проверить два осевых зонда и выбранные номера подканалов.
5. Проверить наличие отчётов и мониторов, отсутствие `[!]`. Настроить реальные условия входа/выхода и выполнить отдельную проверку стационарного массового/теплового баланса на задаче с известными расходом и тепловой мощностью. Для адиабатических стенок ожидается Q_walls≈0; для нагреваемых — проверить знак Q_walls и согласование с изменением потока энтальпии.
6. Повторить экспорт в Internal Interface: два региона, корректный интерфейс и сечения по отдельным регионам.

Автоматические тесты проверяют геометрические метаданные, восстановление ячеек исходных подканалов масками, генерацию макроса, ограничения GUI и отказоустойчивость создания отчётов. При наличии JDK выполняется реальный Java-классификатор и проверка синтаксиса полного макроса. Это не компиляция с библиотеками STAR-CCM+ и не выполнение новых Threshold/энергетических API в решателе; такая приёмка остаётся обязательной.
